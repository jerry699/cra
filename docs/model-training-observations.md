# 模型行为观察记录（供 W3 微调使用）

来源：日常使用中 1.7B（Qwen3-1.7B Q4_K_M，GBNF 约束解码）的真实失败案例。
每条记录：现象 → 证据 → 根因 → 训练启示。微调数据合成时逐条对照。

## OBS-1 · 单例组退化（2026-11-17，v0.1.91/92 实测）

**现象**：6 个互不相关的标签，模型输出 6 个组、每组恰好 1 个标签。下游
`plan()` 按「新组至少 2 个标签」过滤后计划为空 → 整理静默无动作。

**证据**（cra.log）：
```
Tidy Tabs grouped: 6 groups in one pass, sizes 1,1,1,1,1,1
Tidy Tabs grouped pass failed — falling back to two stages
Tidy Tabs topic names: 4
Tidy Tabs: 6 tabs, 4 groups proposed in 63.9 s
Tidy Tabs: plan 2 new groups, 0 joins
```

**根因**：指令自相矛盾——「每个标签必须归入恰好一个组」+「每组至少 2 个」+
「2-4 个组」。当标签互不相关时三条无法同时满足，小模型选择牺牲「每组 2 个」，
产出语法合法但语义无用的单例组。放松指令（允许留标签不归组）后模型矫枉过正，
把本可归组的日常标签也留空（用户观感：整理效果变差），已回退为严格指令。

**工程侧现状**（v0.1.93）：单遍全单例 → 自动降级两阶段；两阶段全单例 → 放弃并
提示「没有共同主题」。日常行为与 0.1.90 一致。

**训练启示**：
1. **这是指令遵循失败，不是能力缺失**——模型需要一个「合理退出」而不是硬凑。
   微调数据必须包含「互不相关标签集 → 输出 0-1 个组」的样本，教模型宁可少整理。
2. GBNF 语法无法表达「标签可以不归组」（assignments 语法强制全覆盖）——
   语法层改成可选覆盖（id 可缺席），或者靠训练让模型在给定语法内输出
   「杂项/稍后读」组之外的行为，需要二选一。
3. 合成数据配比建议：相关标签集（正常分组）: 部分相关 : 完全不相关 ≈ 6:3:1，
   并在 system 指令中明确「少于 2 个可归组的标签时输出空 groups」。
4. 评测用例：6 个全不相关标签 → 期望输出单例组数量为 0（现在为 6）；
   已加入 eval 的方向，见 recall-eval.py 旁的 tidy-eval。

## OBS-2 · 单遍 vs 两阶段的取舍（2026-11-16/17）

单遍 grouped（一次决定组名+分配）快 ~30s，但遇到矛盾指令退化时无自愈能力；
两阶段（先命名 4 主题，再分配）慢但稳。守卫链（单遍失败→两阶段）是正确架构，
微调后的模型如果单遍稳定率 >98%，可以考虑砍掉两阶段回退省 30s。

## OBS-3 · 现有教训（历史，仍然有效）

- 2B 会「全部塞进 topic 0」（一锅端），已有守卫：≥3 主题 + ≥10 标签 + 全部同
  主题 → 放弃。1.7B 未观察到此模式。
- 0.6B 通用指令遵循不足（few-shot 复读），这就是 W3 专用微调的动机：
  任务格式固定（GBNF），微调可消除指令随机性。
- 中文标题 → 英文下载名的怪癖：few-shot 里加中文例子部分解决——
  **微调数据应全中文**，从根上消除。

## OBS-4 · 中国支付链路是拦截器禁区（2026-11-17，用户实付场景发现）

阿里云买域名付款：finance.aliyun.com 收银台嵌淘宝收银台 iframe，后者调
acs.m.taobao.com（API 网关）和 ynuf.alipay.com（设备指纹/风控）——三个域
都在通用广告清单上，全部被第三方拦截 → error.taobao.com。Arc（无拦截器）
能完成支付。

**工程修复**（0.1.94）：同集团豁免（alibaba/ant、tencent、unionpay、jd、
meituan 五个集团互不拦），CRA_BLOCKER_DEBUG=1 可打印每次拦截。

**对产品/模型的启示**：
1. 通用西方广告清单直接用于中国浏览器是系统性风险——中国互联网的"追踪域"
   常常同时是风控/登录/支付承重域（ynuf.alipay.com 双重身份）。未来若做
   AI 智能拦截（如模型判断该不该拦），训练数据必须包含这类"双重身份域"
   的正面样本，且支付场景的代价权重远高于广告漏拦。
2. 原则：拦截器的失败模式必须是"多看了广告"，绝不是"付不了款"。
   所有判断规则都要用这条校验。

## OBS-5 · 支付失败的全链路取证（2026-11-17，CDP 双浏览器对照）

**现象**：阿里云收银台点「支付宝支付」→ 服务端 302 到 http://err.taobao.com/error1.html（交易被拒）。

**逐层排除**（司南 vs Arc，同一订单，双方 CDP 抓包对照）：
| 层 | 结果 |
|---|---|
| 内容拦截器（内置） | 0.1.95 集团豁免后不再拦支付链（mmstat/ynuf 放行） |
| uBlock Origin 扩展 | 曾拦 ynuf.alipay.com（um.js 设备指纹家）→ umidToken=占位符 → 停用后令牌变真实值，**但仍被拒** |
| POST 内容 | 两边结构完全一致（submitPayInfo/真实 umidToken/collina 两边都空） |
| Cookie | 司南 44 个 ⊇ Arc 27 个（淘宝系全家桶都在） |
| UA / UA-CH 品牌指纹 | 完全一致（'Chromium 156'，Arc 也报 Chromium） |
| 代理/指纹保护/https 门 | 全关 |
| **TLS/HTTP2 指纹** | **唯一剩下的差异层**：CEF 与 Arc 的 Chromium 是不同编译产物，握手指纹不同，阿里风控（baxia）检测 TLS 指纹 |

**结论**：不是 fork 代码问题、不是设置问题、停用扩展后也不是扩展问题——是 CEF 编译产物在阿里风控眼里与真 Chrome 的 TLS 层差异。此类检测对 JS 与常规抓包不可见。

**产品对策**（待验证）：WebKit 引擎跑支付站点——真 Safari TLS 栈，风控无从识别。首次 WebKit 测试无效（当时 uBlock 还在杀 um.js），需 uBlock 关闭状态下重测（Webkit 分区需重登阿里云一次）。若通 → 「支付站点自动 Safari 引擎」立项（双引擎即护城河）。

**工具沉淀**：--remote-debugging-port=9222 免重建抓包；CDP capture 脚本（全 target 跟随、POST body、302 Location）；cookie 对照；UA-CH 探针。中国电商支付问题取证的标准流程。

### OBS-5 终局修正（同日晚些，全数据清除实验）

- **TLS 指纹假设被证伪**：本地 TLS 探针抓两边 ClientHello 实测——密码套件/扩展/曲线/ALPN/版本完全一致（哈希差异仅 GREASE 随机填充）。
- **真根因**：设备档案信誉。uBlock 拦 um.js → umid 占位符 → 连续拒单 → 阿里风控把该「设备档案」标记为高危（服务端记忆）→ 请求层修什么都无效。
- **解法**：清除阿里系全部站点数据（Cookie+localStorage+IndexedDB）→ 全新设备档案 → 立即通过。
- **产品启示**：(1) 支付失败的 UX 应提示「清除站点数据后重登」；(2) 第三方扩展的隐私清单是「设备档案毒化」的常见来源，发布说明需警示；(3) AI 拦截/隐私功能必须把「设备档案污染」列为一级风险——它是一次写入、长期生效的服务端惩罚，比单次请求失败严重得多。

### OBS-5 用户反证实验的最终修正（uBlock 复启用例）

用户重新启用 uBlock 后支付**依然成功**（支付宝扫码页正常）——这推翻了「设备档案信誉」的单因子结论。修正后的两因子模型：

1. **路由因子（决定性）**：阿里云统一登录在 aliyun 域种下淘宝通行证 Cookie（cookie2/_tb_token_/havana_lgc2_0/_hvn_lgc_/unb/uc 系列）。收银台服务端见到 havana 标记 → 订单路由进淘宝交易通道；罐子干净（如 Arc）→ 直连支付宝扫码通道。
2. **通道内因子（次要）**：淘宝交易通道校验 umid 设备令牌；uBlock 拦 um.js 时令牌是占位符 → 该通道必拒。直连支付宝通道不依赖 umid → uBlock 在场也无碍。

**为何清库有效**：全量清除同时移除了 havana Cookie（切换回直连通道）和坏 umid 档案——两个因子一起消失。我此前把功劳单一记给「设备信誉」是把清库的双变量实验误读了。教训：清库实验是「一次清两个变量」的粗粒度实验，下结论要列出所有被同时改变的变量。

**未验证的遗留**：havana Cookie 在下次阿里云登录后可能重新累积，届时收银台或再切回淘宝通道。若发生，同样的全清可以再解；根治需要研究 aliyun 登录的 Cookie 种植机制或与服务端交互确认路由规则。

## OBS-6 · 转写模型升级 A/B：Belle-turbo 否决（2026-11-18）

候选：Belle-whisper-large-v3-turbo-zh（q5_0, 574MB, hf-mirror uosx/Belle-whisper-large-v3-turbo-zh-ggml-quantized, sha256 bab0d61935b3f75e…）vs 现用 whisper-small（466MB）。同一合成中文语音（含领域词摇粒绒/羊羔绒/尺码/压胶）：

- 专有词错误率相同（两边都错，靠 polish() 拿标题纠错解决——这正是该通道存在的理由）
- turbo 优势 = 简体+自动标点；代价 = 2.6× 慢（6s 音频 16s→42s；10 分钟视频约 27→70 分钟）
- Intel 6 核上不可接受 → 不入目录、不改默认。模型文件留在 ~/Library/Application Support/Cra/Models/ggml-belle-large-v3-turbo-zh-q5_0.bin 供用户自试（WhisperService 的解析列表不含它，不影响默认）。

**蒸馏管线现状盘点**（比记忆中完整）：polish() 纠错已存在（含领域词表+标题参照）；B 站专用链路（__playinfo__ 音频 DASH + AI 字幕兜底 + wbi API 修 SPA 竞态）；通用 <video>/<audio> src 兜底；MAP-REDUCE 双遍摘要；notesDirectory 设置 UI 已有。**剩余边界**：MSE 流媒体（抖音）不可能（无直链）、YouTube（签名+网络）不做——B 站优先 + 通用兜底就是当前合理边界。蒸馏改进项至此关闭，除非用户实测提出新痛点。
